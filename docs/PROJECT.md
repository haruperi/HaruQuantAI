# HaruQuantAI Project Specification

> **Status:** Backend reset baseline. Kernel and UI retained; replacement backend
> not yet implemented.

## 1. Product goal

Build a local-first quantitative research workstation in which independently
developed components can coexist in the filesystem, memory, capability registry,
and execution graph without hidden coupling. The workstation will eventually
support data acquisition, strategy construction, simulation, optimization,
robustness analysis, portfolios, exports, and controlled external integrations.

No backend product capability is currently marked complete. The retained UI is
a UX prototype and the retained kernel is a candidate foundation, not proof of
the future architecture.

## 2. Ratified system laws

### SC-01 Locality of Behavior

Everything specific to one quantitative concept—implementation, parameter
schema, defaults, bounds, outputs, warm-up, missing-data rules, optimizer
semantics, lowering/export contributions, and generic UI metadata—resides in one
cohesive plugin file.

### SC-02 Orthogonality

Adding, changing, disabling, or removing a plugin requires no source edit to an
unrelated plugin, host engine, or schema-expressible UI. Catalog visibility and
explicit invalidation of documents that reference the changed plugin are allowed;
ambient mutation and unrelated graph changes are not.

### SC-03 Explicit Typed Interfaces

Components connect through immutable typed capability tokens and declared slots.
No component depends on a global service locator, import-time registry mutation,
or another component's private implementation.

### SC-04 Hierarchical / Algebraic Composition

Strategies and workflows are immutable, versioned algebraic documents composed
from typed nodes and ports. The same document is edited by the UI, generated by
algorithms or AI, executed by engines, optimized, persisted, and exported.

### SC-05 Schema-Driven Self-Description

Plugins expose machine-readable parameters, constraints, optimization bounds,
inputs, outputs, compatibility, and presentation hints. Within the supported UI
renderer vocabulary, a new backend plugin requires no frontend source edit.

## 3. Current implementation inventory

| Area | State | Current truth |
|---|---|---|
| Kernel | Retained / under review | Standard-library capability, lifecycle, events, runtime, and logging primitives |
| UI | Retained prototype | React/TypeScript workstation using frontend mocks and browser-local state |
| Backend host | Missing | No composition root, gateway, persistence, jobs, workers, or integrations |
| Plugin SDK/catalog | Missing | No ratified metamodel or discovery implementation |
| Quantitative plugins | Missing | No production indicators, rules, metrics, tasks, or exporters |
| Algebra AST | Missing | No shared typed strategy/workflow document |

## 4. Required architecture sequence

1. Ratify the minimal kernel surface and remove ambient discovery/effect paths.
2. Define the universal plugin metamodel, identity/version policy, catalog
   snapshot, algebra AST, and compatibility rules.
3. Define the host boundary for discovery, enablement, execution, persistence,
   jobs, telemetry, and gateway transport.
4. Define the UI catalog client, schema renderer vocabulary, algebra editor, and
   separation between remote truth, drafts, and view state.
5. Prove a thin vertical slice with one plugin before scaling plugin families.

Each step requires its own implementation plan and owner approval.

## 5. System-wide acceptance

- A new schema-expressible plugin is added as one file and appears in every
  applicable consumer without editing a central registry, engine, or UI source.
- Removing that plugin leaves unrelated catalog entries, runtime order, and
  documents unchanged; referencing documents become explicitly unavailable but
  remain losslessly readable.
- UI, generator, simulator, optimizer, and exporter consume the same versioned
  algebra and plugin identities.
- Unsupported versions and schemas fail closed with attributed diagnostics.
- Reproducible runs freeze plugin/catalog fingerprints, data identity, settings,
  seeds, and engine version.
- No live or irreversible external action occurs without separate explicit
  authorization.

## 6. Current non-goals

- Claiming parity with StrategyQuant X or any external product.
- Preserving the deleted backend's APIs or database schemas.
- Treating UI mocks as production behavior.
- Supporting arbitrary new UI interactions from unconstrained metadata; dynamic
  UI is bounded by a ratified generic renderer vocabulary.

## 7. Open decisions

- Final plugin metamodel and stable identity grammar.
- Discovery mechanism, enablement policy, and catalog fingerprint format.
- Algebra node/port type system and migration policy.
- Host persistence and process topology.
- UI schema vocabulary and custom-extension security boundary.
- Kernel event and logging disposition.
